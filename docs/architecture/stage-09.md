# مرحلهٔ ۹ — معماری پرداخت

پرداخت کامل از Snapshot نوبت گرفته می‌شود؛ مبلغ عدد صحیح ریال است. تنها Provider فعال، Mock است و هیچ وجه واقعی منتقل نمی‌شود. ورود شماره موبایل/رمز باقی مانده و ایمیل و OTP اضافه نشده‌اند.

## مرز Provider و حالت آزمایشی

`payments/providers.py` قرارداد create، verify، status، refund و refund_status و قابلیت‌های درگاه را تعریف می‌کند. `processing.py` آماده‌سازی، تماس بیرونی و ثبت نتیجه را در سه بخش جدا اجرا می‌کند؛ هنگام تماس Provider هیچ تراکنش برنامه باز نیست. UUID تلاش/بازپرداخت کلید ثابت درگاه است. Timeout نتیجهٔ نامعلوم دارد، مبلغ را آزاد نمی‌کند و تلاش جدید باز نمی‌سازد.

Mock در جدول‌های مستقل `mock_orders` و `mock_refunds` ذخیره می‌شود؛ ساخت دوبارهٔ سرویس یا قطع برنامه، نتیجهٔ درگاه را پاک نمی‌کند. این شبیه‌ساز برای توسعه است و پایگاه دادهٔ مالیِ یک درگاه مستقل واقعی محسوب نمی‌شود. هر دو جدول tenant-aware و دارای FORCE RLS هستند؛ دریافت‌های واقعیِ برنامه در PaymentTransaction جدا ثبت می‌شوند.

`SALONBOOK_MOCK_PAYMENTS_ENABLED=false` پیش‌فرض است. پیش‌نمایش موقت صریحاً آن را فعال می‌کند؛ مدیر سپس با `POST /api/v1/payments/mock-account` حساب آزمایشی سالن را می‌سازد. `SALONBOOK_PAYMENTS_MODE=test` تعیین‌کنندهٔ is_test نوبت است؛ مرورگر نمی‌تواند آن را تغییر دهد. حالت live فعلاً Provider ندارد و پرداخت را رد می‌کند. برای درگاه آینده، Adapter و تنظیم حساب/راز و mode سرور اضافه می‌شود؛ منطق نوبت و اسناد به درگاه وابسته نیست. Adapter باید تطبیق هویت، نتیجهٔ قطعی، استعلام و idempotency خود را مطابق همین قرارداد اثبات کند؛ برای درگاه فاقد تضمین لازم، عملیات مبهم نیازمند رسیدگی می‌ماند.

## مسیرها

همهٔ مسیرهای زیر پیشوند `/api/v1/payments` دارند. به‌جز callback، ورود لازم است. نوشتن‌ها Origin و CSRF معتبر می‌خواهند. ایجاد پرداخت و درخواست Refund نیز Idempotency-Key دارند.

| روش و مسیر | نتیجه |
|---|---|
| POST /mock-account | ایجاد حساب Mock با مجوز salon.manage |
| POST / | ساخت تلاش پرداخت برای appointment_id |
| GET /?appointment_id=… | تلاش‌های همین نوبت؛ limit≤100 و offset≤10000 |
| GET /{id} | وضعیت Intent، Attempt، نوبت، دریافت/تخصیص، شماره رسید و Refundها |
| GET /{id}/mock-checkout | جزئیات پرداخت آزمایشی؛ صفحهٔ HTML پرداخت در مرحلهٔ ۱۱ |
| POST /{id}/mock-checkout | انتخاب نتیجهٔ شبیه‌ساز و سپس Verify واقعیِ سمت سرور |
| POST /{id}/verify | استعلام مجدد با همان شناسهٔ درگاه |
| POST /{id}/callback | فقط بیدارکردن کار پایدار؛ پاسخ عمومی accepted با کد 202 |
| GET /invoices/{appointment_id} | فاکتور و اقلام immutable |
| POST /transactions/{id}/refunds | درخواست amount و reason؛ رزرو سقف بازپرداخت |
| GET /refunds/{id} | وضعیت مستقل بازپرداخت |
| POST /refunds/{id}/approve | تأیید و اجرای بازپرداخت یا نمایش نتیجهٔ نامعلوم |
| POST /refunds/{id}/cancel | لغو فقط پیش از تأیید |
| GET /refunds/{id}/credit-note | سند برگشتِ بازپرداخت موفق |

خروجی Mock یکی از `success`، `failure`، `cancel`، `timeout` یا `amount_mismatch` است. نتیجه یک بار تعیین می‌شود؛ تکرار همان نتیجه مجاز و تغییر آن رد می‌شود. timeout درگاه را موفق می‌کند اما اولین استعلام را نامعلوم برمی‌گرداند، تا بازیابی آزمایش شود. برای پرداخت دیرهنگام کافی است بعد از لغو یا انقضا نتیجهٔ موفق انتخاب شود.

مالک دارای appointment.read_own و مدیر دارای finance.read در محدودهٔ لاین، اطلاعات مالی را می‌بینند. پرداخت برای دیگری علاوه بر finance.read، appointment.manage می‌خواهد. کارمند صرفاً منتسب به نوبت مجوز مشاهدهٔ پرداخت ندارد. درخواست و تأیید Refund نیازمند payment.refund در همان لاین است؛ الزام دو تأییدکنندهٔ متفاوت در این نسخه تعریف نشده است.

## اثر مالی و هم‌زمانی

Merchant، شناسهٔ سفارش، شناسهٔ تراکنش، ارز، مقدار صحیح و زمان دریافت بررسی می‌شوند. ورودی callback ــ از جمله success یا مبلغ ارسالی ــ سند پرداخت نیست و ذخیره نمی‌شود. Callbackهای تکراری یک رویداد browser-return دارند و استعلام را جلو می‌اندازند؛ دادهٔ مالی به تماس‌گیرندهٔ ناشناس برگردانده نمی‌شود.

قفل‌ها: lifecycle → CalendarControl اشتراکی → User/Session برای درخواست کاربر → CustomerProfile → EmployeeProfile مرتب → Appointment → Intent/Attempt → Refund. قفل والد Appointment تمام رزروهای Refund همان دریافت را سری می‌کند؛ روی جدول append-only تراکنش، مجوز UPDATE داده نشده است.

دریافت معتبر، رسید، ثبت CAPTURE، تخصیص، قطعی‌سازی Hold معتبر، فاکتور و Outbox در یک Commit ثبت می‌شوند. اگر مهلت حین قطعی‌سازی تمام شود، تخصیص با Savepoint برمی‌گردد اما دریافت حفظ و Refund ساخته می‌شود. دریافت دیرهنگام، پس از لغو، مبلغ نامعتبرِ دریافت‌شده یا دریافت دوم نیز حفظ می‌شود؛ فقط یک دریافت کامل قابل تخصیص است و اضافه‌دریافت به بازپرداخت می‌رود. تعلیق سالن مانع ثبت دریافت/Refund توسط Worker نمی‌شود ولی نوبت تازه قطعی نمی‌شود.

یک کلید ایجاد پرداخت در محدودهٔ کاربر/عملیات/سالن به همان تلاش اشاره می‌کند؛ استفاده برای نوبت متفاوت خطای 409 دارد. نگهداری کلید هفت روز است و کلید منقضی خودکار بازیافت نمی‌شود. بازپخش پرداخت وضعیت **فعلی همان منبع** را برمی‌گرداند؛ بر خلاف پاسخ Snapshot عملیات نوبت، بدنهٔ پرداخت با پیشرفت Verify تغییر می‌کند. کلید جدید هنگام تلاش باز 409 می‌دهد؛ پس از شکست قطعی، تلاش تازه فقط در Hold معتبر و بدون تمدید زمان مجاز است.

فاکتور برای نوبت پولی پس از تخصیص معتبر و برای نوبت رایگان هنگام تأیید صادر می‌شود. هر دریافت رسید خودش را دارد؛ هر Refund موفق CreditNote و ثبت REFUND دارد. اسناد مالی بازنویسی نمی‌شوند. برچسب TEST و is_test همراه مبلغ حفظ می‌شود؛ این اسناد ادعای صورتحساب قانونی/مالیاتی ندارند.

## Refund و کار پس‌زمینه

مجموع درخواست‌های رزروشده، در حال اجرا، نامعلوم و موفق نمی‌تواند از دریافت بیشتر شود. درخواست نامعلوم همچنان سقف را اشغال می‌کند. تأیید تکراری دوباره پول برنمی‌گرداند؛ استعلام refund_status قبل از اجرای مجدد انجام می‌شود. پاسخ موفق Refund نیز باید پذیرنده، تراکنش، مبلغ و ارز یکسان داشته باشد. لغو نوبت طبق سیاست مرحلهٔ ۸، باقیماندهٔ قابل برگشت را خودکار تأیید می‌کند؛ آزادشدن یک درخواست دستی بعد از لغو نیز در دور بعد پوشش داده می‌شود. شکست قطعی Refund خودکار، برای رسیدگی مدیر باقی می‌ماند و کلید جدید خودکار تولید نمی‌شود.

صف کار، **رکورد پایدار Attempt/Refund و زمان next_check_at** است. Worker عمومی Outbox/اعلان هنوز پیاده نشده؛ Outbox سند رویداد است و Worker پرداخت لغوها را از وضعیت پایدار نوبت/دریافت می‌یابد. هر دور حداکثر ۵۰ تلاش، ۵۰ بررسی لغو و ۵۰ Refund می‌گیرد. تکرار ایمن بین چند Worker مجاز است؛ تضمین تحویل دقیقاً یک بار مطرح نیست. فاصلهٔ استعلام ۳۰ ثانیه است. شکست/لغو قطعی تا هفت روز پس از مهلت زیر نظر می‌ماند؛ callback یا Verify صریح می‌تواند بعد از این بازه نیز استعلام را دوباره فعال کند. وضعیت نامعلوم خودکار به شکست تبدیل نمی‌شود.

برای پایگاه دادهٔ ماندگار، پس از migration `0010` مجوزهای `sql/runtime_grants.sql` را اعمال کنید. هر Worker به tenant صریح و حساب runtime نیاز دارد:

```powershell
uv run --no-sync python -m scripts.expire_holds --tenant <UUID> --env-file .env
uv run --no-sync python -m scripts.reconcile_payments --tenant <UUID> --env-file .env
```

گزینهٔ `--once` یک دور اجرا می‌کند. `scripts.serve` Worker راه نمی‌اندازد؛ فرایند Worker باید توسط محیط اجرا زنده نگه داشته شود. `scripts.dev` هر دو Worker را برای همان سالن موقت راه می‌اندازد و هنگام خروج متوقف می‌کند. آزمون واقعی HTTP با `scripts.check_payments_preview` اجرا می‌شود.

Migration 0010 دو جدول شبیه‌ساز، زمان بازبینی Refund و ایندکس‌های صف را اضافه می‌کند؛ دادهٔ قدیمی را تغییر نمی‌دهد. تعداد جدول‌ها ۵۳ است. مرز مرحلهٔ بعد زیرساخت Next.js است؛ فرایند رزرو و صفحهٔ پرداخت مشتری در مرحلهٔ ۱۱ پیاده می‌شوند.
