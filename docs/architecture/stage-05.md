# مرحلهٔ ۵ — مدیریت سالن، Tenant و کاربران

قرارداد جاری ورود، طبق درخواست کاربر، **شمارهٔ موبایل ایران و رمز، بدون ایمیل** است. شماره هنوز با OTP تأیید نمی‌شود. این مرحله Backend را تکمیل می‌کند؛ رابط مدیریتی طبق برنامهٔ اصلی در مراحل Frontend ساخته می‌شود.

## نتیجه و مرز اختیار

هر Salon یک Tenant مستقل است. API سالن از دامنهٔ ثبت‌شده و فعال، Tenant را تعیین می‌کند. مدیر سالن می‌تواند نام سالن، حساب مشتری و کارمند، وضعیت حساب، پروفایل کارمند و نقش‌های همان سالن را مدیریت کند. ساخت سالن با مدیر اولیه، فعال‌سازی دامنه، تعلیق و بستن سالن از ابزار مستقل اپراتور انجام می‌شوند.

کنترل پلتفرم در این مرحله CLI است؛ API عمومی Super Admin یا ورود پلتفرمی ساخته نشده است. اتصال این ابزار دسترسی محدودی دارد و اتصال API نمی‌تواند عملیات آن را انجام دهد. API نیز اتصال دارای مجوزهای کنترل پلتفرم را در startup و تراکنش رد می‌کند.

فایل‌های اصلی:

- `backend/app/modules/tenancy/router.py`: قرارداد HTTP.
- `backend/app/modules/tenancy/management.py`: مدیریت سالن، کاربر، نقش و سقف تفویض در یک تراکنش.
- `backend/app/modules/tenancy/administration.py`: عملیات اپراتور، بدون وابستگی به نشست مرورگر.
- `backend/app/modules/tenancy/locks.py`: هماهنگی تغییر دسترسی و چرخهٔ عمر سالن.
- `backend/scripts/manage_tenants.py`: ابزار اپراتور.
- `backend/alembic/versions/0006_tenant_management.py`: کاتالوگ مجوزها و ارتقای نقش‌های سیستمی موجود.

## قرارداد API

پیشوند تمام مسیرها `/api/v1` است. عملیات تغییردهنده به Cookie نشست، `Origin` صحیح، `X-CSRF-Token` مربوط به همان نشست و JSON نیاز دارند؛ DELETE بدنه لازم ندارد. نشست و مجوز دوباره داخل تراکنش Service بررسی می‌شوند. موفقیت فقط پس از commit برمی‌گردد.

| مسیر | رفتار و مجوز |
|---|---|
| `GET /salon` | مشخصات سالن جاری؛ `salon.read` |
| `PATCH /salon` | تغییر نام؛ `salon.manage` در سطح سالن |
| `PATCH /profile` | تغییر نام نمایشی خود؛ `profile.update` |
| `GET /users` | فهرست کاربران؛ `users.read` در سطح سالن |
| `GET /users/{id}` | مشخصات یک حساب همان سالن؛ `users.read` |
| `POST /users` | حساب مشتری یا کارمند؛ `users.manage` و برای کارمند `staff.manage` |
| `PATCH /users/{id}` | نام نمایشی و فعال/غیرفعال بودن؛ `users.manage` و سقف اختیار نسبت به حساب مقصد |
| `PUT /users/{id}/employee` | ساخت/ویرایش نام عمومی و وضعیت پروفایل کارمند؛ `users.manage` و `staff.manage` در سطح سالن |
| `GET /permissions` | کاتالوگ مجوزها؛ `roles.read` |
| `GET /roles` | نقش‌های فعال سالن و مجوزها؛ `roles.read` |
| `POST /roles` | نقش سفارشی؛ `roles.manage` و سقف تفویض |
| `PUT /roles/{id}` | جایگزینی نام و مجموعهٔ مجوزهای نقش سفارشی؛ `roles.manage` |
| `DELETE /roles/{id}` | حذف نرم نقش سفارشی و لغو انتساب‌های آن؛ `roles.manage` |
| `POST /users/{id}/roles` | انتساب نقش در دامنهٔ مجاز؛ `roles.manage` در همان دامنه |
| `DELETE /role-assignments/{id}` | لغو انتساب و ابطال نشست‌های حساب؛ `roles.manage` در دامنهٔ انتساب |

فهرست کاربران `limit=1..100`، `offset=0..10000` و فیلتر `kind=customer|employee|manager` دارد؛ پاسخ شامل `items, limit, offset, has_more` است. ترتیب `created_at, id` ثابت است. فهرست نقش‌ها نیز limit/offset محدود دارد.

اطلاعات حساب مدیریتی شامل شمارهٔ استاندارد، وضعیت تأیید شماره، نام نمایشی، وضعیت حساب، شناسهٔ پروفایل مشتری، پروفایل کارمند و انتساب‌های فعال است. رمز، hash رمز، توکن و ایمیل در پاسخ نیستند. شناسهٔ مربوط به سالن دیگر مثل شناسهٔ ناموجود، 404 می‌گیرد. کاربر فاقد مجوز 403 می‌گیرد؛ Tenant از بدنه یا `X-Tenant-ID` قابل تغییر نیست.

نمونهٔ ساخت حساب کارمند:

```json
{
  "phone": "09123456789",
  "password": "a-private-password-at-least-15-characters",
  "display_name": "نام کارمند",
  "kind": "employee"
}
```

این حساب، پروفایل مشتری، پروفایل کارمند و دو نقش customer/employee دارد. `kind=customer` فقط پروفایل و نقش مشتری می‌سازد. تعیین مدیر از طریق انتساب صریح نقش انجام می‌شود؛ API ثبت‌نام عمومی همچنان فقط مشتری می‌سازد. شمارهٔ تکراری در همان سالن برای مدیر 409 است و حساب قبلی تغییر نمی‌کند؛ همان شماره در سالن دیگر مستقل است.

برای تبدیل مشتری موجود به کارمند: ابتدا پروفایل او را با `PUT /users/{id}/employee` ایجاد کنید، سپس نقش employee را بدهید. پروفایل کارمند وضعیت ارائهٔ خدمت است؛ وضعیت User ورود را کنترل می‌کند. غیرفعال کردن پروفایل کارمند، خود حساب مشتری را نمی‌بندد. غیرفعال کردن User فوراً نشست‌هایش را باطل می‌کند. مراحل رزرو باید هر دو وضعیت را بررسی کنند.

## نقش‌ها و قواعد تفویض

| نقش سیستمی | دامنهٔ انتساب | اختیار جدید این مرحله |
|---|---|---|
| customer | TENANT | مشاهدهٔ سالن و ویرایش نام خود |
| employee | TENANT | مشاهدهٔ سالن و ویرایش نام خود؛ مجوزهای کار اجرایی در مرحلهٔ ۶ |
| line_manager | LINE با لاین فعال همان سالن | اختیارات لاین؛ بدون مدیریت حساب مشترک یا تنظیمات کل سالن |
| salon_manager | TENANT | مدیریت سالن، کاربران، کارکنان و نقش‌ها |

نقش‌های سیستمی قابل ویرایش/حذف نیستند. نقش سفارشی از مجوزهای شناخته‌شده ساخته می‌شود. تغییر تعریف نقش فقط با `roles.manage` در سطح TENANT مجاز است؛ تمام مجوزهای قبلی و جدید باید در سقف اختیار مدیر باشند. مدیر دارای اختیار LINE نمی‌تواند با ساخت نقش به سطح سالن برسد.

هر انتساب TENANT باید `line_id=null` داشته باشد و انتساب LINE به لاین فعال همان سالن نیاز دارد. مدیر فقط مجوزهای موجود در دامنهٔ خودش را می‌دهد یا پس می‌گیرد. مدیریت وضعیت حسابی با اختیارات بالاتر نیز ممنوع است. نقش محلی نمی‌تواند دسترسی پلتفرم ایجاد کند.

حذف یا غیرفعال کردن آخرین مدیر فعال دارای موبایل ممنوع است، حتی با دو درخواست هم‌زمان. انتقال مدیریت با افزودن مدیر دوم و سپس لغو نقش اول انجام می‌شود. حذف واقعی حساب یا سوابق انجام نمی‌شود؛ غیرفعال‌سازی تاریخچه را حفظ می‌کند. نقش حذف‌شده و انتساب لغوشده نیز برای Audit باقی می‌مانند؛ کد نقش حذف‌شده دوباره مصرف نمی‌شود.

تغییر نقش/مجوز یا وضعیت حساب، `auth_version` را افزایش می‌دهد و تمام نشست‌ها و قابلیت‌های تاریخی حساب را باطل می‌کند. فعال‌سازی مجدد حساب یا بازگرداندن مجوز، نشست قبلی را زنده نمی‌کند. افزایش اختیار نیز ورود مجدد می‌خواهد.

## هماهنگی و Audit

ترتیب قفل‌ها: lifecycle سالن → management سالن → User → Session. تراکنش‌های احراز هویت قفل اشتراکی lifecycle دارند؛ عملیات اپراتور قفل انحصاری می‌گیرند. در نتیجه تعلیق با ورود یا درخواست در حال اجرا رقابت نمی‌کند: تراکنش قبلی تمام می‌شود، سپس تعلیق همهٔ نشست‌ها را باطل می‌کند. وضعیت سالن و ثبت دامنه، پس از گرفتن قفل و داخل تراکنش دوباره بررسی می‌شوند.

نوشتن‌های مدیریتی در یک سالن سری می‌شوند تا تغییر هم‌زمان نقش و غیرفعال‌سازی دو مدیر باعث حذف آخرین مدیر یا چرخهٔ قفل حساب‌ها نشود. این قفل‌ها جایگزین RLS یا مجوز نیستند. بازهٔ انتظار و زمان اجرای تراکنش همچنان محدود است و شکست، کل تغییر و Audit آن را rollback می‌کند.

Audit موفق در همان تراکنش ذخیره می‌شود: Actor، Tenant، عمل، شناسهٔ موجودیت، Request ID، IP و تغییرات مجاز مانند وضعیت قبل/بعد یا مجموعهٔ مجوزها. نام شخص فقط به‌عنوان فیلد تغییرکرده مشخص می‌شود؛ شماره، رمز و توکن در metadata نیستند. عملیات اپراتور در `platform_audit_logs` با دلیل و نام حساب اتصال دیتابیس ثبت می‌شود؛ این عامل، حساب وب Super Admin نیست. رخدادهای HTTP ناموفق در لاگ امن درخواست ثبت می‌شوند.

## ساخت و ادارهٔ سالن

پس از `alembic upgrade head`، مدیر دیتابیس `sql/runtime_grants.sql` را دوباره اجرا کند تا فقط مجوز تغییر ستون name سالن به API اضافه شود. برای ابزار اپراتور، `sql/control_grants.sql` گروه NOLOGIN به نام `salonbook_control` می‌سازد. یک LOGIN اختصاصی عضو این گروه شود؛ هیچ عضویتی به حساب API ندهید. اتصال owner برای عملیات آفلاین مهاجرت مجاز است ولی حساب اختصاصی محدود ترجیح دارد.

اتصال اپراتور از متغیر `SALONBOOK_CONTROL_DATABASE_URL` خوانده می‌شود؛ در تنظیمات API، فایل ثبت‌شده در Git یا آرگومان خط فرمان قرار نمی‌گیرد. از پوشهٔ backend:

```powershell
uv run --no-sync python -m scripts.manage_tenants create --name "نام سالن" --hostname salon.example.com --manager-phone 09123456789 --manager-name "مدیر سالن" --reason "ایجاد سالن پس از بررسی مالک"
```

رمز مدیر اولیه دو بار به‌صورت مخفی پرسیده می‌شود و حداقل ۱۵ نویسه دارد. سالن، تنظیمات، کنترل تقویم، نقش‌ها، حساب مدیر و Audit در یک تراکنش ساخته می‌شوند. شناسهٔ Tenant چاپ می‌شود. دامنه ابتدا غیرفعال است؛ پس از بررسی مالکیت و اتصال صحیح دامنه:

```powershell
uv run --no-sync python -m scripts.manage_tenants domain --tenant <TENANT_UUID> --hostname salon.example.com --operation activate --confirm-domain-control --reason "مالکیت و مسیریابی دامنه بررسی شد"
uv run --no-sync python -m scripts.manage_tenants show --tenant <TENANT_UUID>
uv run --no-sync python -m scripts.manage_tenants status --tenant <TENANT_UUID> --status SUSPENDED --reason "تعلیق توسط اپراتور"
```

فعال‌سازی دامنه، تأیید صریح اپراتور است؛ ابزار ادعای بررسی خودکار DNS ندارد و DNS/Reverse Proxy را تغییر نمی‌دهد. دامنه باید جداگانه در Allowed Hosts و تنظیمات استقرار مجاز باشد. `domain --operation add` دامنهٔ دوم را غیرفعال ثبت می‌کند و `disable` آن را از مسیر ورود خارج می‌کند. دامنهٔ یک سالن به سالن دیگر منتقل نمی‌شود.

وضعیت‌ها ACTIVE، SUSPENDED و CLOSED هستند. SUSPENDED قابل بازگشت به ACTIVE است؛ CLOSED نهایی است. هیچ‌کدام دادهٔ مالی/کاربر را حذف نمی‌کند.

برای سالن قدیمی بدون مدیر، اپراتور پس از بررسی مالکیت حساب موجود می‌تواند اولین مدیر را مشخص کند:

```powershell
uv run --no-sync python -m scripts.manage_tenants bootstrap-manager --tenant <TENANT_UUID> --user <USER_UUID> --reason "مالکیت حساب بررسی شد"
```

این ابزار حساب فعالِ دارای موبایل همان سالن را می‌پذیرد، نشست‌های قبلی را می‌بندد و در حضور مدیر فعال دیگر اجرا نمی‌شود. مدیران بعدی از API نقش‌ها تعیین می‌شوند. حساب قدیمی فاقد شناسهٔ موبایل ابتدا با ابزار مرحلهٔ ۴ و بررسی هویت اپراتور به شماره متصل می‌شود.

## پیش‌نمایش و ادامه

`python -m scripts.dev` پیش‌نمایش عمومی را اجرا می‌کند. برای آزمون تعاملی با مدیر اولیه، `python -m scripts.dev --manager-phone 09123456789` را اجرا و رمز دلخواه را در prompt مخفی وارد کنید. شمارهٔ نمونه را با شمارهٔ آزمایشی خود جایگزین کنید؛ هیچ پیامکی ارسال نمی‌شود. هر اجرای پیش‌نمایش دیتابیس موقت مستقل دارد.

`python -m scripts.check_management_preview` یک پیش‌نمایش جدا با مدیر و رمز تصادفی در حافظه اجرا می‌کند، گردش واقعی HTTP را می‌سنجد و فقط محیط موقت خودش را جمع می‌کند. گزارش نهایی آزمون‌ها در [verification-stage-05.md](../backend/verification-stage-05.md) است.

مرحلهٔ بعد، پس از تأیید جداگانهٔ کاربر، **مرحلهٔ ۶: لاین‌ها، خدمات و اتصال کارکنان به لاین/خدمت** است. پروفایل کارمند این مرحله مبنای آن است؛ زمان‌بندی و سیاست‌های رزرو مربوط به مراحل ۷ و ۸ هستند. OTP همچنان برای بعد باقی است.
