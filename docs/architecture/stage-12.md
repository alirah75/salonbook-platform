# مرحلهٔ ۱۲ — پنل مدیران و کارکنان

مسیر `/dashboard` فضای کاری سالن و مسیر `/platform` پنل مستقل مدیر کل است. هر دو فارسی، راست‌به‌چپ، سازگار با موبایل و دارای پوستهٔ روشن و تیره‌اند. ورود همچنان با موبایل و رمز است؛ فرم یا جریان ایمیل اضافه نشده و OTP برای مرحلهٔ بعدی احراز هویت باقی مانده است.

## فضای کاری سالن

منو و عملیات از مجوزهای واقعی `GET /api/v1/dashboard/context` ساخته می‌شوند، نه از نام نقش. نقش اختصاصی هم با همین قاعده کار می‌کند. API هر درخواست را با نشست، مجوز تازه، سالن فعال، محدودهٔ لاین و RLS بررسی می‌کند؛ مخفی‌بودن دکمه جایگزین کنترل سرور نیست.

| بخش | رفتار |
|---|---|
| نمای کلی و نوبت‌ها | آمار وضعیت و فهرست صفحه‌بندی‌شدهٔ روز، فیلتر لاین مجاز، نام مشتری و کارمند، زمان به وقت سالن |
| عملیات نوبت | انجام خدمت و عدم حضور برای کارمند مسئول؛ لغو و جابه‌جایی برای مدیر مجاز؛ دلیل، نسخهٔ مورد انتظار، کلید جلوگیری از تکرار و کنترل زمان/تعارض روی سرور |
| لاین و خدمت | ساخت و ویرایش تعریف‌ها در سطح سالن؛ قیمت، مدت و فاصلهٔ قبل/بعد برای لاین مجاز؛ فعال و غیرفعال‌سازی |
| تیم و مهارت | عضویت کارمند در لاین، فعال‌بودن همکاری و تعیین خدمات قابل ارائه |
| برنامه و مرخصی | ساخت تقویم، همهٔ بازه‌های هفتگی با تاریخ اعتبار، تعطیلی یا ساعت استثنایی، درخواست مرخصی کارمند و تصمیم مدیر |
| حساب‌ها | ایجاد حساب موبایلی مشتری یا کارمند، نام و فعال‌بودن حساب، پروفایل کارمند |
| نقش‌ها | دیدن مجوزها، ایجاد/ویرایش نقش اختصاصی و واگذاری/برداشتن نقش با محدودهٔ سالن یا لاین |
| تنظیمات | نام سالن و قواعد رزرو، پرداخت موقت، فاصلهٔ زمانی، مهلت لغو و افق رزرو |

`GET /dashboard/overview` فقط مجوزهای `appointment.read` و `appointment.read_assigned` را برای انتخاب نوبت‌ها به کار می‌برد. مجوز مشتری برای دیدن نوبت شخصی، آمار کاری کارمند یا مدیر لاین را گسترده نمی‌کند. مرز روز بر اساس منطقهٔ زمانی سالن به UTC تبدیل می‌شود. شمارنده‌ها از همان فیلتر SQL فهرست به دست می‌آیند. مبلغ کارمند بدون مجوز مالی مطابق قرارداد موجود پنهان است؛ حق دیدن مبلغ نوبت شخصی خودش در API قبلی حفظ می‌شود.

انتخاب‌های صفحه‌بندی‌شده دکمهٔ ادامه دارند؛ فهرست ناوبری لاین‌ها حداکثر ۵۰۰ مورد است و در صورت عبور از این حد درخواست به‌صراحت متوقف می‌شود. خواندن دوره‌ای نمای کلی دادهٔ نمایشی را تازه می‌کند. خطای تازه‌سازی مجوز، کنترل‌های کاری را پنهان می‌کند. تغییر دسترسی‌ها طبق رفتار مرحلهٔ ۵ ورودهای مربوط را باطل می‌کند. ساعات ورودی مستقل از منطقهٔ زمانی دستگاه در منطقهٔ زمانی سالن تفسیر می‌شوند.

## مدیر کل: سرویس و هویت مستقل

`app.platform.main:create_platform_app` در API سالن mount نمی‌شود. پیشوند آن `/platform/api/v1` است. سرویس پلتفرم اتصال جداگانه با گروه `salonbook_platform` دارد؛ گروه آفلاین `salonbook_control` به سرویس وب داده نمی‌شود. API عادی اتصال با مجوزهای پلتفرم را در زمان راه‌اندازی رد می‌کند؛ سرویس پلتفرم نیز owner، superuser، bypass، DDL و اتصال عضو گروه runtime سالن را رد می‌کند.

`sql/platform_grants.sql` فقط مجوزهای مورد نیاز دفتر سالن‌ها، ایجاد مدیر اولیه، دامنه، تغییر وضعیت و ثبت رویداد را می‌دهد. دسترسی مستقیم به نوبت‌ها، تقویم، پرداخت‌ها و دفتر مالی داده نمی‌شود. سیاست SELECT بین‌سالن‌ها فقط برای متادیتای جدول `salons` و فقط برای گروه پلتفرم است. RLS اجباری سایر داده‌های سالن برقرار می‌ماند؛ ایجاد سالن و ابطال نشست‌های آن با tenant context و قفل‌های قبلی انجام می‌شود.

هویت مدیر کل در `platform_users` است. Migration `0011` شمارهٔ موبایل یکتا و نام نمایشی را اضافه می‌کند و اطلاعات ایمیل تاریخی را بدون تبدیل خودکار یا ساخت حساب جدید نگه می‌دارد. هیچ ورود ایمیلی وجود ندارد. حساب‌های قدیمی بدون شمارهٔ موبایل وارد این پنل نمی‌شوند. بازگردانی migration در حضور دادهٔ موبایلی یا مرجع مجوز فعال، به‌جای حذف اطلاعات متوقف می‌شود؛ روی دیتابیس بدون دادهٔ جدید قابل بازگردانی و اجرای مجدد است.

نشست پلتفرم تصادفی، هش‌شده و مستقل است: cookie مخصوص با `HttpOnly`، `SameSite=Strict`، مسیر `/platform` و در Production `Secure`. سقف مطلق ۸ ساعت، مهلت بی‌کاری ۳۰ دقیقه، حداکثر ۱۰ نشست فعال و بررسی فعال‌بودن حساب/مجوز در هر درخواست اعمال می‌شود. تغییرهای وب Origin دقیق، JSON، CSRF و بدنهٔ محدود دارند. شمارنده‌های مشترک PostgreSQL برای ورود، حساب را به ۸ تلاش در ۱۵ دقیقه و سرویس را به ۶۰ تلاش در دقیقه محدود می‌کنند. کلید حساب در این جدول HMAC است؛ شماره یا رمز در آن نگهداری نمی‌شود. خروج و ورود ثبت رویداد دارند.

مدیر کل می‌تواند سالن با حساب مدیر اولیه بسازد، وضعیت را میان فعال/تعلیق تغییر دهد، دامنه اضافه یا غیرفعال کند و تاریخچهٔ عملیات را ببیند. فعال‌سازی دامنه نیازمند تصدیق صریح بررسی مالکیت و مسیریابی است؛ پنل ادعای بررسی خودکار DNS ندارد. دلیل عملیات و شناسهٔ مدیر کل در `platform_audit_logs` ثبت می‌شود. بستن نهایی سالن و ورود به‌جای کاربران در این پنل ارائه نمی‌شود.

## اجرا و بررسی محلی

```powershell
cd backend
uv run --no-sync python -m scripts.dev --public-port 3000 --dashboard-demo
```

در ترمینال دوم `cd frontend` و `npm run dev`. متغیرهای `.env.example` شامل API سالن در پورت ۸۰۰۰ و API مستقل پلتفرم در ۸۰۰۱ هستند. رابط‌ها:

- <http://127.0.0.1:3000/dashboard>
- <http://127.0.0.1:3000/platform>

پیش‌نمایش یک PostgreSQL موقت می‌سازد و workerهای انقضا و پرداخت Mock را اجرا می‌کند. فلگ `--dashboard-demo` فقط در همین دیتابیس، حساب مدیر سالن، مدیر لاین، کارمند و مدیر کل را با **رمز تصادفی** می‌سازد. شماره‌ها و رمزها در `backend/.local/dashboard-demo.json` ذخیره می‌شوند؛ پوشهٔ `.local` از Git مستثناست. با راه‌اندازی دوباره، دیتابیس و رمزها عوض می‌شوند. هیچ حساب پیش‌فرض یا ارتقای خودکار مشتری در محیط ماندگار ایجاد نمی‌شود. در این پیش‌نمایش فقط supervisor محلی دو سرویس را میزبانی می‌کند؛ در استقرار هر سرویس process و secret مستقل دارد.

آزمون مرورگر داشبورد به همین فلگ نیاز دارد. بدون فایل حساب آزمایشی، این سناریوها به‌صراحت skip می‌شوند؛ اجرای ثبت‌شدهٔ این مرحله با حساب‌ها و API واقعی است.

## راه‌اندازی ماندگار

ابتدا migrationها را با اتصال owner اجرا و `sql/platform_grants.sql` را با اپراتور دیتابیس اعمال کنید. یک LOGIN مستقل و محدود فقط عضو گروه پلتفرم بسازید؛ مشخصات آن را در پیکربندی API سالن قرار ندهید. نخستین حساب پلتفرم با اتصال آفلاین `DATABASE_MIGRATION_URL` و `python -m scripts.platform_admin --phone ... --name ... --reason ...` ساخته می‌شود؛ رمز به صورت مخفی دریافت می‌شود و حساب موجود بازنویسی نمی‌شود.

سرویس جدا با `python -m scripts.serve_platform` و این تنظیمات صریح اجرا می‌شود:

| تنظیم | مقدار/معنا |
|---|---|
| `SALONBOOK_PLATFORM_DATABASE_URL` | اتصال psycopg همان LOGIN محدود پلتفرم |
| `SALONBOOK_PLATFORM_AUTH_KEY` | کلید Fernet مستقل از سالن، از secret store |
| `SALONBOOK_PLATFORM_PUBLIC_ORIGIN` | origin دقیق پنل، مثلاً `https://admin.example.com` |
| `SALONBOOK_PLATFORM_ENVIRONMENT` | `production`؛ HTTP فقط در development loopback پذیرفته می‌شود |

Reverse proxy باید مسیر `/platform/api/v1` را بدون تغییر به سرویس پلتفرم و `/api/v1` سالن را به API عادی بفرستد و Host درست را حفظ کند. هیچ bridge توسعه در Production فعال نیست. این مرحله انتشار عمومی انجام نداده است؛ سخت‌سازی استقرار طبق برنامه در مرحلهٔ ۱۴ بررسی می‌شود.

گزارش‌های درآمد و نمودارهای مالی در مرحلهٔ ۱۳ هستند. این مرحله فقط شمارنده‌های عملیاتی نوبت و مجوزهای موجود را عرضه می‌کند. گزارش بررسی: [مرحلهٔ ۱۲](../frontend/verification-stage-12.md).
