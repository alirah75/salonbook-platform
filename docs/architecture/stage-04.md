# مرحلهٔ ۴ — ورود با موبایل، بدون ایمیل

قرارداد جاری با درخواست صریح کاربر اصلاح شد: **ثبت‌نام و ورود با شمارهٔ موبایل ایران و رمز عبور؛ ایمیل در محصول وجود ندارد؛ OTP بعداً اضافه می‌شود.** این تصمیم جایگزین ورود ایمیلی و بازیابی ایمیلی در طراحی اولیه است. این کار اصلاح مرحلهٔ ۴ است و ورود به مرحلهٔ ۵ محسوب نمی‌شود.

ثبت‌نام، ورود، Current User، تغییر رمز با رمز فعلی، خروج، خروج از همهٔ دستگاه‌ها، فهرست و لغو نشست‌ها و زیرساخت RBAC فعال‌اند. **۱۸۸ آزمون موفق** و جریان کامل HTTP واقعی بررسی شده است؛ [گزارش جاری](../backend/verification-mobile-login.md).

## قرارداد API

| مسیر زیر /api/v1/auth | ورودی یا کاربرد |
|---|---|
| GET /csrf | دریافت Cookie موقت و CSRF پیش از ورود |
| POST /register | phone، password و display_name؛ پاسخ عمومی ۲۰۲ |
| POST /login | phone و password؛ Cookie نشست و پاسخ Session |
| GET /me | کاربر جاری، وضعیت تأیید موبایل و CSRF نشست |
| POST /change-password | current_password و new_password؛ نیازمند نشست و CSRF |
| POST /logout | خروج از نشست جاری |
| POST /logout-all | لغو تمام نشست‌های کاربر |
| GET /sessions | نشست‌های فعال، بدون شناسهٔ محرمانهٔ Cookie |
| DELETE /sessions/{identifier} | لغو نشست متعلق به کاربر جاری |

نمونهٔ ثبت‌نام؛ این مقادیر فقط نمونه‌اند:

```json
{
  "phone": "09123456789",
  "password": "choose-a-private-long-password",
  "display_name": "کاربر نمونه"
}
```

فیلد email در ورودی پذیرفته نمی‌شود و در پاسخ کاربر وجود ندارد. ورودی‌های Role، Tenant و phone_verified نیز از کاربر پذیرفته نمی‌شوند. پاسخ کاربر شامل id، tenant_id، phone، phone_verified، display_name و roles است.

مسیرهای forgot-password، reset-password، verify-email و resend-verification و کد SMTP/Worker ایمیل حذف شدند. بازیابی رمز بدون دانستن رمز فعلی تا پیاده‌سازی OTP فعال نیست. تغییر رمز در نشست معتبر با رمز فعلی اکنون کار می‌کند و همهٔ نشست‌های قبلی را باطل می‌کند.

## یکسان‌سازی شماره

شماره‌های `09123456789`، `+989123456789`، `00989123456789` و ارقام فارسی/عربی به `+989123456789` تبدیل می‌شوند. فاصله، خط تیره و پرانتز متعارف پذیرفته می‌شوند؛ متن، extension، شمارهٔ ثابت، شمارهٔ ناقص و کشور دیگر رد می‌شوند.

تشخیص ساختار و نوع MOBILE بر پایهٔ [کتابخانهٔ phonenumbers](https://github.com/daviddrysdale/python-phonenumbers) نسخهٔ قفل‌شدهٔ 9.0.40 است. اعتبار قالب و پیش‌شماره اثبات نمی‌کند که شماره فعال یا متعلق به ثبت‌نام‌کننده است. بنابراین `phone_verified` تا تأیید واقعی همواره false است.

یک شماره در هر سالن فقط یک حساب می‌سازد؛ همان شماره در سالن دیگر می‌تواند حساب مستقل داشته باشد. Unique Constraint روی tenant_id + phone_normalized جلوی رقابت هم‌زمان را می‌گیرد. ثبت‌نام تکراری رمز یا مشخصات حساب قبلی را تغییر نمی‌دهد و همان پاسخ عمومی را برمی‌گرداند.

Rate Limit بعد از یکسان‌سازی اعمال می‌شود؛ تغییر قالب شماره شمارندهٔ تلاش را دور نمی‌زند. شمارهٔ خام یا استانداردشده در لاگ یا bucket خام نوشته نمی‌شود؛ bucket با HMAC ساخته می‌شود.

| identity/security.py | Argon2id، Token تصادفی، Hash و HMAC |
| identity/sessions.py | نشست، انقضا، لغو و صدور نشست مشترک برای رمز و OTP آینده |
| identity/context.py | حل Tenant از Host ثبت‌شده و کنترل فعال‌بودن سالن |
| identity/dependencies.py | Origin، CSRF و guard مجوز HTTP |

| scripts/bind_login_mobile.py | اتصال صریح شماره به حساب قدیمی، فقط برای نگهداری مورد اعتماد |

این جداسازی اجازه می‌دهد تأیید OTP بعداً به همان SessionService متصل شود؛ لازم نیست Cookie، RBAC یا مجوزها دوباره ساخته شوند. بررسی مجوز در Serviceهای تجاری آینده نیز باید داخل تراکنش انجام شود؛ dependency مسیر به‌تنهایی جای کنترل مالکیت و شرایط کسب‌وکار را نمی‌گیرد.

## امنیت نشست و رمز

Session همچنان opaque و سمت سرور است؛ JWT/Refresh Token جداگانه نداریم. Token با ۲۵۶ بیت تصادف ساخته و فقط Hash آن ذخیره می‌شود. Cookie روی HTTPS نام `__Host-salonbook-session`، Secure، HttpOnly، SameSite=Lax و Path=/ دارد و Domain ندارد. محیط production ورود HTTP را رد می‌کند؛ پیش‌نمایش HTTP محلی Cookie جدا با نام salonbook-dev-session دارد.

عمر مشتری ۲۴ ساعت مطلق و ۱۲۰ دقیقه بیکاری است؛ کارکنان و مدیران ۸ ساعت و ۳۰ دقیقه. فعالیت، حذف نرم، نسخهٔ اعتبار کاربر و fingerprint مجوز در هر استفاده بررسی می‌شوند. تغییر مؤثر نقش نشست قبلی را رد می‌کند؛ نشست ردشده با بازگرداندن نقش زنده نمی‌شود. نقش‌ها و دسترسی‌ها در هر درخواست از دیتابیس خوانده می‌شوند.

رمز جدید ۱۵ تا ۱۲۸ نویسه و بدون trim یا بریدن است. Argon2id با ۶۴ MiB حافظه، سه iteration و parallelism=1 استفاده می‌شود؛ rehash در ورود موفق پشتیبانی شده است. چهار عملیات Hash هم‌زمان در هر process مجاز است. رمز، Cookie و CSRF در لاگ ثبت نمی‌شوند.

Rate Limit پیش‌فرض در پنجرهٔ ۱۵ دقیقه برای هر عملیات، ۱۰ تلاش برای شماره و ۵۰ تلاش برای IP است. شمارنده‌ها در تراکنش مستقل ثبت می‌شوند؛ شکست ورود آن‌ها را rollback نمی‌کند. Header جعلی X-Tenant-ID، X-Forwarded-Host یا IP جای دادهٔ مورد اعتماد را نمی‌گیرد.

برای register/login ابتدا `/csrf` فراخوانی می‌شود؛ Cookie موقت و مقدار JSON باید همراه POST در Header `X-CSRF-Token` ارسال شوند. Origin همان دامنه و Content-Type برابر application/json الزامی است. برای عملیات نشست از CSRF پاسخ login یا `/me` استفاده می‌شود. Header لازم در مستندات تعاملی نمایش داده شده است.

مبنای کنترل‌های حفظ‌شده: [نشست OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)، [رمز OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) و [CSRF OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## مهاجرت داده

نسخهٔ Schema اکنون `0005` است. ستون‌های phone_normalized و phone_verified_at اضافه شده‌اند؛ شمارهٔ استاندارد در دیتابیس نیز قید قالب دارد. ایمیل قدیمی برای سازگاری migration nullable شده است و ثبت‌نام جدید مقدار ایمیل ذخیره نمی‌کند. ستون‌های تاریخی ایمیل و Token قدیمی برای حذف‌نشدن ناخواستهٔ داده نگه داشته شده‌اند و API یا Worker فعال مصرفشان نمی‌کند.

شمارهٔ تماس قدیمی `users.phone` خودکار به شمارهٔ ورود تبدیل نشده است. آن داده قبلاً صرفاً اطلاعات تماس بوده و ممکن است مشترک، اشتباه یا تأییدنشده باشد. migration برای حساب فاقد شماره، شمارهٔ ساختگی ایجاد نمی‌کند و رمز یا شناسهٔ کاربر را عوض نمی‌کند.

برای حساب قدیمی، مدیر مورد اعتماد باید پس از تطبیق هویت شماره را صریحاً متصل کند. ابزار نگهداری زیر با اتصال runtime و Tenant مشخص اجرا می‌شود؛ این ابزار هیچ API عمومی ندارد:

```powershell
uv run --no-sync python -m scripts.bind_login_mobile --tenant TENANT_UUID --user USER_UUID --phone 09123456789 --env-file .env
```

این فرمان را فقط با UUIDهای واقعی و شمارهٔ تطبیق‌داده‌شده اجرا کنید. تغییر شماره تمام نشست‌ها و قابلیت‌های قبلی حساب را باطل و Audit ثبت می‌کند؛ شماره همچنان تأییدنشده است. شمارهٔ تکراری در همان سالن رد می‌شود. این ابزار در این جلسه روی دادهٔ واقعی کاربر اجرا نشده است.

حساب قدیمی بدون اتصال شماره از مسیر ورود جدید قابل ورود نیست؛ انتقال چنین حساب‌هایی باید پیش از جابه‌جایی نسخهٔ عملیاتی برنامه‌ریزی شود. Downgrade به 0004 در حضور حساب بدون ایمیل عمداً ناموفق و rollback می‌شود تا دادهٔ ساختگی یا حذف داده رخ ندهد. هر دو رفتار با دادهٔ قدیمی واقعی در PostgreSQL موقت آزمایش شده‌اند.

## مرز OTP آینده

اکنون هیچ کد پیامکی ارسال یا پذیرفته نمی‌شود و Endpoint نمایشی OTP وجود ندارد. آماده‌سازی فعلی شامل شمارهٔ یکتا و استاندارد، وضعیت phone_verified_at، guard شمارهٔ تأییدشده و صدور مشترک Session است. مالکیت شماره تا دریافت و بررسی OTP اثبات نشده است.

برای پیاده‌سازی OTP آینده باید Challenge مخصوص Tenant، شماره و هدف، عمر کوتاه، شمارندهٔ اتمیک تلاش، محدودیت ارسال مجدد، Provider پیامک و مصرف یک‌باره ساخته شوند. کد کم‌آنتروپی OTP باید با HMAC کلیددار محافظت شود؛ Hash سادهٔ Token تصادفی قدیمی جای آن را نمی‌گیرد. پس از تأیید، وضعیت شماره و ایجاد/تعویض نشست در تراکنش معتبر انجام می‌شود. تغییر شماره و بازیابی رمز نیز به همین اثبات متصل خواهند شد.

guard عملیات نیازمند مالکیت شماره اکنون برای کاربر تأییدنشده رد می‌کند. قبل از فعال‌کردن جریان رزرو واقعی که تأیید شماره را لازم دارد، OTP باید تکمیل شود. این شرط با ورود اولیهٔ phone/password یکی نیست.

## اجرای محلی و آزمون

از پوشهٔ backend، با Docker فعال:

```powershell
uv sync --frozen --python 3.13
uv run --no-sync python -m scripts.dev --port 8000
```

در ترمینال دوم:

```powershell
uv run --no-sync python -m scripts.check_auth_preview --port 8000
```

پیش‌نمایش دیتابیس، سالن نمونه، نقش‌ها و کلید تصادفی مخصوص همان اجرا را می‌سازد. ایمیل/پیامک و صندوق ایمیل محلی ندارد. با Ctrl+C فقط همان دیتابیس موقت پاک می‌شود. [API Docs](http://127.0.0.1:8000/api/v1/docs) ورودی phone را نشان می‌دهد.

برای دیتابیس ماندگار migration تا 0005، Grantهای runtime، دامنه و نقش‌های provisioning و `SALONBOOK_AUTH_KEY` پایدار لازم است؛ متغیرهای SMTP حذف شده‌اند. تنظیمات نشست و Rate Limit در `.env.example` موجودند. انتشار، ظرفیت و بررسی نهایی امنیت به مراحل مربوط تعلق دارند.

مدیریت سالن و کاربران مرحلهٔ بعد است و پس از تأیید کاربر آغاز می‌شود؛ OTP طبق درخواست کاربر به زمان بعد موکول شده است.
