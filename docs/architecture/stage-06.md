# مرحلهٔ ۶ — لاین‌ها، خدمات و کارکنان

این مرحله مدیریت Line، Service، LineService، EmployeeLine و EmployeeService را به Backend اضافه می‌کند. حساب و پروفایل کارمند از مرحلهٔ ۵ استفاده می‌کنند؛ حذف نرم کارمند و فهرست تخصص‌ها نیز تکمیل شده است. ورود همچنان موبایل و رمز، بدون ایمیل است؛ OTP برای بعد باقی می‌ماند.

## نتیجهٔ اجرایی

مدیر سالن می‌تواند لاین و خدمت بسازد، نام و وضعیت آن‌ها را تغییر دهد، برای هر لاین قیمت و مدت جدا تعیین کند، کارمند اضافه/غیرفعال/حذف کند و تخصص او را به خدمات همان لاین متصل کند. یک کارمند می‌تواند در چند لاین و با چند خدمت کار کند.

مدیر لاین فقط تنظیمات و ارتباط‌های لاین‌های مجاز خودش را تغییر می‌دهد. تغییر خدمت مشترک، حذف کل لاین و تغییر یا حذف پروفایل مشترک کارمند به مجوز سطح سالن نیاز دارند. ارتباط با کارمند، شماره یا حساب او را در اختیار مدیر لاین قرار نمی‌دهد.

کاتالوگ عمومی، بدون ورود، لاین‌ها و خدمات فعال و نام عمومی کارکنان فعالِ واجد شرایط را نشان می‌دهد. این خروجی **زمان آزاد یا امکان رزرو در ساعت مشخص** نیست؛ محاسبهٔ زمان آزاد متعلق به مرحلهٔ ۷ است.

## قرارداد HTTP

پیشوند `/api/v1` است. همهٔ فهرست‌ها `limit=1..100` با مقدار پیش‌فرض ۲۵ و `offset=0..10000` دارند؛ پاسخ شامل `items, limit, offset, has_more` و ترتیب ثابت نام/شناسه است. مسیرهای مدیریتی نشست لازم دارند؛ POST/PATCH/PUT/DELETE، Origin و CSRF نشست را نیز بررسی می‌کنند. ورودی اضافه مانند tenant_id رد می‌شود.

| مسیر | رفتار و دامنهٔ اختیار |
|---|---|
| `GET /lines` | فهرست لاین‌های تحت اختیار؛ `catalog.manage` یا `staff.assign` |
| `GET /lines/{id}` | جزئیات لاین مجاز |
| `POST /lines` | ساخت لاین؛ `catalog.manage` در سطح سالن |
| `PATCH /lines/{id}` | نام، slug، وضعیت؛ `catalog.manage` در همان لاین |
| `DELETE /lines/{id}` | حذف نرم لاین؛ `catalog.manage` در سطح سالن |
| `GET /services` و `GET /services/{id}` | تعاریف مشترک خدمات همان سالن؛ برای مدیر کاتالوگ یا انتساب‌ها |
| `POST /services` | ساخت خدمت؛ `catalog.manage` در سطح سالن |
| `PATCH /services/{id}` | نام، code، توضیح و وضعیت؛ `catalog.manage` در سطح سالن |
| `DELETE /services/{id}` | حذف نرم خدمت مشترک؛ `catalog.manage` در سطح سالن |
| `GET /lines/{line}/services` | قیمت، مدت و وضعیت خدمات لاین مجاز |
| `PUT /lines/{line}/services/{service}` | ساخت/جایگزینی پیشنهاد خدمت؛ `catalog.manage` در همان لاین |
| `DELETE /lines/{line}/services/{service}` | قطع ارتباط خدمت با لاین |
| `GET /employees` | فهرست پروفایل کارکنان؛ `staff.manage` در سطح سالن |
| `DELETE /employees/{id}` | حذف نرم کارمند؛ `staff.manage` و `users.manage` در سطح سالن و سقف اختیار حساب مقصد |
| `GET /lines/{line}/employee-candidates` | فقط شناسه و نام عمومی کارکنان فعال برای انتخاب؛ `staff.assign` همان لاین |
| `GET /lines/{line}/employees` | کارکنان متصل و وضعیت مؤثر هر ارتباط؛ `staff.assign` همان لاین |
| `PUT /lines/{line}/employees/{employee}` | اتصال/تغییر وضعیت عضویت کارمند؛ `staff.assign` همان لاین |
| `DELETE /lines/{line}/employees/{employee}` | قطع عضویت کارمند در لاین |
| `GET /lines/{line}/employees/{employee}/services` | تخصص‌های کارمند در لاین |
| `PUT /lines/{line}/employees/{employee}/services/{service}` | اتصال/تغییر وضعیت تخصص، فقط وقتی هر دو ارتباط والد وجود دارند |
| `DELETE /lines/{line}/employees/{employee}/services/{service}` | قطع تخصص در همان لاین |

ساخت کارمند جدید همان `POST /users` با `kind=employee` است. این عملیات حساب، پروفایل مشتری، پروفایل کارمند و نقش‌های لازم را اتمی می‌سازد. ویرایش نام عمومی یا فعال/غیرفعال کردن کارمند از `PUT /users/{user_id}/employee` انجام می‌شود. برای مشتری موجود، ابتدا همین مسیر پروفایل را بسازد و سپس نقش employee از API نقش‌ها داده شود. `employee_id` شناسهٔ پروفایل است و با `user_id` فرق دارد.

کاتالوگ عمومی:

| مسیر | خروجی |
|---|---|
| `GET /catalog/lines` | لاین‌های فعال همان دامنه |
| `GET /catalog/lines/{line}/services` | خدمات فعال و قیمت/مدت/بافر همان لاین |
| `GET /catalog/lines/{line}/services/{service}/employees` | فقط `id` و `public_name` کارکنان واجد شرایط |

Tenant در تمام مسیرها از دامنهٔ فعال تعیین می‌شود و وضعیت سالن/دامنه داخل تراکنش هم بررسی می‌شود. UUID متعلق به سالن دیگر در نتیجهٔ مدیر مجاز یا کاتالوگ عمومی دیده نمی‌شود. مدیر فاقد دامنهٔ اختیار، 403 می‌گیرد؛ شناسهٔ ناموجود برای مدیر مجاز، 404 است.

## ورودی و ترتیب راه‌اندازی

۱. لاین با `name` و `slug` بسازید؛ slug از حروف کوچک انگلیسی، عدد و خط تیره بین بخش‌ها تشکیل می‌شود. نام فارسی مجاز است.

۲. خدمت مشترک با `name` و `code` بسازید؛ code حروف کوچک انگلیسی، عدد، خط تیره یا زیرخط بین بخش‌ها دارد. توضیح اختیاری حداکثر ۴۰۰۰ نویسه است. PATCH می‌تواند توضیح را با null پاک کند؛ نام یا وضعیت null مجاز نیست.

۳. خدمت را به لاین وصل کنید:

```json
{
  "price_amount": 1000000,
  "currency": "IRR",
  "duration_minutes": 30,
  "buffer_before_minutes": 5,
  "buffer_after_minutes": 10,
  "is_free": false,
  "is_active": true
}
```

مبلغ، عدد صحیح ریال است؛ اعشار، رشته، bool، مقدار منفی یا خارج از bigint رد می‌شود. خدمت رایگان باید هم مبلغ صفر و هم is_free=true داشته باشد؛ مبلغ مثبت با is_free=true نیز ممنوع است. این قاعده در API و دیتابیس یکسان است. مدت ۱ تا ۱۴۴۰ دقیقه و هر بافر ۰ تا ۲۴۰ دقیقه است. مبلغ/مدت/بافر متعلق به LineService است و تغییر یک لاین به لاین دیگر سرایت نمی‌کند.

۴. کارمند را به لاین وصل کنید؛ سپس همان کارمند را به خدمات موجود آن لاین وصل کنید. بدنهٔ هر دو PUT، `{"is_active": true}` است و `{}` نیز پیش‌فرض فعال را می‌گیرد. عضویت در لاین به‌تنهایی به معنی انجام همهٔ خدمات آن نیست.

PUT ارتباط‌ها وضعیت کامل ارتباط را تعیین می‌کند و 200 برمی‌گرداند. تکرار آن رکورد یا شناسهٔ جدید نمی‌سازد. یکتایی tenant/line/service و tenant/employee/line/service در دیتابیس نیز اعمال می‌شود. POST لاین و خدمت 201 و DELETE موفق 204 برمی‌گرداند؛ نامک/کد تکراری 409 است. کدهای لاین/خدمت حذف‌شده برای حفظ هویت تاریخی مجدداً مصرف نمی‌شوند.

## وضعیت مؤثر و حذف

فعال بودن تخصص نیازمند تمام این موارد است: سالن و دامنهٔ معتبر، Line فعال، Service فعال، LineService فعال، EmployeeProfile فعال، User فعال، EmployeeLine فعال و EmployeeService فعال؛ هیچ‌کدام نباید حذف نرم شده باشند. پاسخ مدیریتی وضعیت ذخیره‌شدهٔ خود ارتباط را در `is_active` و وضعیت نهایی را در `effective_active` نشان می‌دهد. خروجی عمومی فقط وضعیت مؤثر فعال را انتخاب می‌کند.

غیرفعال کردن والد، تنظیمات فرزندان را حفظ می‌کند؛ با فعال‌سازی دوبارهٔ والد، ارتباط‌هایی که خودشان هنوز فعال هستند دوباره مؤثر می‌شوند. در مقابل، **DELETE ارتباط‌های وابسته را هم حذف نرم می‌کند**؛ بازاتصال والد تخصص‌های حذف‌شده را خودکار فعال نمی‌کند. بازاتصال هر ارتباط از PUT خودش با شناسهٔ قبلی انجام می‌شود.

حذف لاین، پیشنهادهای خدمات و عضویت‌ها/تخصص‌های همان لاین را حذف نرم می‌کند؛ نقش‌های محدود به همان لاین لغو و نشست‌های دارندگان آن نقش‌ها باطل می‌شوند. لاین دیگر، تعریف مشترک خدمت و پروفایل کارمند حفظ می‌شوند. حذف خدمت مشترک، پیشنهادها و تخصص‌های همان خدمت را در همهٔ لاین‌های همان سالن حذف نرم می‌کند.

حذف کارمند، پروفایل و ارتباط‌های کاری او را حذف نرم و نقش سیستمی employee را لغو می‌کند و نشست‌های قبلی را می‌بندد. حساب مشتری و نقش مدیریت مستقل او حذف نمی‌شوند. بازگرداندن پروفایل از مسیر موجود users ممکن است؛ نقش employee و ارتباط‌های حذف‌شده باید صریحاً دوباره داده شوند. غیرفعال کردن پروفایل صرفاً ارائهٔ خدمت را متوقف می‌کند؛ غیرفعال کردن User ورود را هم متوقف می‌کند.

## حفظ نوبت‌ها و هماهنگی تراکنش

اگر نوبت AWAITING_PAYMENT یا CONFIRMED با `occupied_ends_at` بعد از زمان جاری به منبع وابسته باشد، حذف یا غیرفعال کردن آن منبع با خطای `upcoming_bookings` و وضعیت 409 رد می‌شود. این کنترل برای لاین، خدمت، پیشنهاد لاین، کارمند، عضویت و تخصص و همچنین مسیر قدیمی غیرفعال‌سازی User/Employee اجرا می‌شود. کاربر باید ابتدا نوبت را از مسیر مجاز لغو، جابه‌جا یا تعیین تکلیف کند؛ این مرحله نوبت را خودکار لغو نمی‌کند.

نگه‌داشت منقضی که هنوز در وضعیت AWAITING_PAYMENT مانده نیز تا تغییر وضعیت توسط موتور رزرو مانع حذف است. دادهٔ تاریخچه و snapshotها حفظ می‌شوند. تغییر قیمت/مدت/نام برای رزروهای جدید است؛ مبلغ، زمان و نام‌های ثبت‌شده در AppointmentItem قبلی تغییر نمی‌کنند.

ترتیب قفل‌ها به این صورت توسعه یافته است:

`tenant lifecycle → tenant management (writes) → CalendarControl → User → Session → domain records`

کاتالوگ برای خواندن قفل اشتراکی CalendarControl می‌گیرد؛ نوشتن قفل انحصاری می‌گیرد و پس از موفقیت version را افزایش می‌دهد. APIهای قبلی که وضعیت حساب یا پروفایل کارمند را عوض می‌کنند نیز همین قرارداد را رعایت می‌کنند. تغییر نام شخصیِ غیرعمومی، تغییر نقش یا ورود عادی نیازی به قفل تقویم ندارند. تمام کنترل مجوز، قاعدهٔ نوبت، تغییر و Audit در یک تراکنش هستند؛ شکست چیزی را نصفه ذخیره نمی‌کند و version هم تغییر نمی‌کند.

موتور رزرو مرحلهٔ ۸ باید از قفل اشتراکی **پیش از خواندن شرایط فعال بودن و پیش از قفل User** استفاده کند و تا ثبت نوبت نگه دارد. آزمون رقابتی همین قرارداد را شبیه‌سازی می‌کند: حذف کارمند پشت تراکنش رزرو منتظر می‌ماند، بعد نوبت تازه را می‌بیند و با 409 رد می‌شود. این هماهنگی جایگزین قید عدم هم‌پوشانی PostgreSQL نیست.

## مهاجرت و اجرا

نسخهٔ جاری schema، `0007` است. migration مجوز `staff.assign` را به نقش‌های سیستمی مدیر سالن و مدیر لاین می‌دهد و قید قیمت رایگان/پولی را دقیق‌تر می‌کند. نقش سفارشی خودکار تغییر نمی‌کند. نشست‌های مدیرانی که مجوزشان تغییر کرده، به ورود مجدد نیاز دارند. RLS در پایان مهاجرت برای همهٔ جداول مربوط، فعال و FORCE است.

اگر دادهٔ قدیمی مبلغ مثبت را با is_free=true ذخیره کرده باشد، مهاجرت کامل rollback می‌شود؛ مبلغ یا سابقه به‌طور خودکار تغییر نمی‌کند. اپراتور باید مورد را بررسی و علامت/مبلغ درست را مشخص کند، سپس مهاجرت را دوباره اجرا کند. آزمون مهاجرت، حفظ داده در این حالت و downgrade/reupgrade را بررسی می‌کند. هیچ جدول جدید یا مجوز دیتابیس عمومی اضافه نشده است.

از پوشهٔ backend:

```powershell
uv run --no-sync python -m scripts.dev --manager-phone 09123456789
uv run --no-sync python -m scripts.check_catalog_preview
```

دستور اول پیش‌نمایش با مدیر اولیه و prompt مخفی رمز می‌سازد؛ شماره را با شمارهٔ آزمایشی خود عوض کنید. دستور دوم مستقل است و یک سرور و دیتابیس موقت دیگر با رمز تصادفی در حافظه می‌سازد، گردش HTTP واقعی را بررسی و فقط محیط خودش را جمع می‌کند. هیچ ایمیل یا پیامکی ارسال نمی‌شود.

[گزارش آزمون مرحلهٔ ۶](../backend/verification-stage-06.md) نتیجهٔ نهایی را ثبت می‌کند. مرحلهٔ بعد، پس از تأیید جداگانهٔ کاربر، **مرحلهٔ ۷: موتور زمان‌بندی، ساعت کاری، استراحت، مرخصی، تعطیلی و محاسبهٔ زمان‌های آزاد** است.
