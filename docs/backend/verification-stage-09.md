# بررسی مرحلهٔ ۹

اجرای نهایی هستهٔ Backend: **۳۵۲ آزمون موفق در 388.56s**؛ ۲۵ آزمون جدید پرداخت. آزمایش‌ها روی PostgreSQL موقت، runtime role محدود و FORCE RLS اجرا شدند.

پوشش جدید: مبلغ سمت سرور، کلید تکراری/متفاوت، یک تلاش باز، شکست و retry بدون تمدید Hold، Verify تکراری/هم‌زمان، Merchant/Order نامعتبر، مبلغ متفاوت، دریافت دوم، لغو/انقضا و عبور مهلت حین تأیید، قطع پس از ایجاد سفارش و پیش از ثبت محلی، Refund نامعلوم و بازیابی بدون برگشت دوم، سقف رزرو هم‌زمان، CreditNote، آزادشدن رزرو دستی بعد از لغو، حالت live بدون پذیرش Mock، tenant isolation و نبود تراکنش باز هنگام تماس Provider.

`scripts.check_payments_preview` با HTTP واقعی موفق شد: نوبت، پرداخت، بازپخش، Verify، تأیید، فاکتور/رسید، Refund جزئی و سند برگشت، سپس بازپرداخت باقی‌مانده توسط Worker مستقل. این آزمون پس از تغییر preview در مرحلهٔ ۱۰ نیز دوباره موفق شد؛ خروجی در `payment-http-check.log` است. اطلاعات ورود چاپ نمی‌شود.

Ruff check، قالب‌بندی ۱۳۷ فایل، mypy برای ۱۳۶ فایل، سه خروجی schema و uv lock با ۴۶ بسته موفق‌اند. migration 0010 با upgrade/downgrade/reupgrade و Alembic check بررسی شد. مدل اکنون ۵۳ جدول دارد و دو جدول جدید Mock نیز FORCE RLS دارند.

خطای پیدا و اصلاح‌شده در تست واقعی: SUM(bigint) در PostgreSQL مقدار Decimal می‌دهد؛ پیش از ثبت ماندهٔ Refund در JSON، تبدیل دقیق به int انجام می‌شود. آزمون بازپرداخت باقی‌مانده پس از لغو این مسیر را پوشش می‌دهد.

این گزارش تأیید پرداخت واقعی یا آمادگی Production نیست؛ فقط Mock فعال است. اعلان و Worker عمومی Outbox، درگاه واقعی و گزارش مالی در محدودهٔ این مرحله نیستند.
