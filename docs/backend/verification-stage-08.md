# گزارش بررسی مرحلهٔ ۸

تاریخ: ۲۰۲۶-۱۰-۰۳. محیط: ویندوز، Python 3.13، PostgreSQL 18 موقت با نقش runtime فاقد مالکیت و BYPASSRLS، migration 0009.

## اجرای کامل

```text
327 passed in 297.59s (0:04:57)
```

۱۹ آزمون جدید نوبت‌دهی و تمام آزمون‌های پیشین در اجرای نهایی موفق‌اند. Ruff check موفق، هر ۱۲۴ فایل مطابق قالب، mypy برای ۱۲۳ فایل بدون خطا، سه خروجی schema مطابق کد و lockfile با ۴۶ پکیج بررسی شده‌اند. ۵۱ جدول و ۴۳ جدول تحت RLS حفظ شده‌اند؛ فقط تنظیم مهلت عدم حضور و مجوزهای نوبت به schema/دادهٔ سیستمی افزوده شده‌اند.

## شواهد رفتاری

- ساخت Hold با مبلغ و اقلام سمت سرور، محدودیت یک Hold برای مشتری و رد فیلد مبلغ ارسالی.
- همان کلید/بدنه، همان پاسخ؛ بدنهٔ متفاوت با همان کلید رد می‌شود. خطای مقصد اشغال نیز تا استفاده از کلید تازه بازپخش می‌شود.
- تأیید رایگان بدون PaymentIntent یا رسید ساختگی؛ جلوگیری از تأیید پولی بدون شواهد معتبر و تأیید با دادهٔ منطبقِ صرفاً آزمایشی.
- انقضای Hold هنگام فرمان، پاسخ ۴۰۹ همراه با commit وضعیت EXPIRED؛ بازپخش خطا، تاریخچه یا Outbox تکراری نمی‌سازد.
- پاک‌سازی وضعیت Hold منقضی در مسیر ثبت، قید ظرفیت و یک Hold را برای نوبت تازه آزاد می‌کند.
- دو Worker هم‌زمان یک نوبت را فقط یک بار منقضی می‌کنند؛ Worker سالن دیگر به آن دسترسی ندارد.
- جابه‌جایی با قیمت و مدت اصلی پس از تغییر کاتالوگ؛ مقصد اشغال، نوبت قدیمی را تغییر نمی‌دهد. اقلام Snapshot ثابت می‌مانند.
- بستهٔ چند خدمت، ترتیب اقلام، مبلغ جمع‌شده و بافر داخلی مشترک.
- مهلت لغو ثبت‌شده، منع استثنای مشتری، استثنای حسابرسی‌شدهٔ مدیر سالن و محدودیت لاین مدیر.
- کارمند منصوب مبلغ را نمی‌بیند؛ تکمیل زودهنگام و عدم حضور پیش از زمان لازم رد می‌شوند. وضعیت پایانی قابل لغو یا جابه‌جایی نیست.
- رد ساعت خارج از برنامه، شروع خارج از شبکه، سالن بسته، شناسهٔ سالن دیگر و CSRF نامعتبر.

## آزمون‌های هم‌زمانی

۱. **۵۰ مشتری متمایز با نشست معتبر، درخواست HTTP هم‌زمان برای یک ظرفیت:** دقیقاً یک پاسخ ۲۰۱ و ۴۹ پاسخ ۴۰۹؛ فقط یک Appointment و یک Outbox ثبت شده است. هیچ رزرو هم‌پوشان ایجاد نشده است. برای تفکیک صحت رزرو از محدودیت پذیرش اتصال، این آزمون pool برابر ۵۰، انتظار قفل ۱۰ ثانیه و statement timeout برابر ۱۵ ثانیه دارد؛ ادعای عملکرد تنظیمات پیش‌فرض یا SLA نیست.

۲. ده درخواست هم‌زمان با یک Idempotency-Key، همگی یک شناسه و همان پاسخ را می‌گیرند؛ یک رکورد idempotency و یک رخداد ثبت می‌شود.

۳. رقابت ثبت نوبت و تعطیلی سالن با Event هماهنگ شده است: نوبت قفل اشتراکی تقویم را نگه می‌دارد، تغییر برنامه منتظر می‌ماند و پس از ثبت نوبت تازه، با ۴۰۹ رد می‌شود.

۴. دو درخواست برای یک کارمند در دو لاین، فقط یک نوبت موفق می‌سازند. دو جابه‌جایی با expected_version یکسان نیز فقط یک تغییر موفق دارند.

۵. تزریق خطای deadlock پس از درج نوبت، rollback کامل و اجرای دوباره را بررسی می‌کند؛ فقط یک نوبت و یک Outbox نهایی باقی می‌مانند.

## HTTP واقعی

سرور و دیتابیس مستقل موقت ساخته و موارد زیر از طریق HTTP بررسی شدند: ساخت منابع و برنامه، Hold، بازپخش پاسخ، منع تأیید بدون پرداخت، لغو Hold، رزرو رایگان، جابه‌جایی، GET وضعیت جاری، لغو و تاریخچه.

```text
PASS: real HTTP booking, idempotent replay, payment evidence guard,
free confirmation, rescheduling, cancellation and history.
```

اسکریپت: `backend/scripts/check_appointments_preview.py`. محیط آزمون پس از پایان جمع شد؛ هیچ پیامک، ایمیل یا درگاه واقعی فراخوانی نشد و رمز/توکن چاپ نشد.

## پیش‌نمایش و مرز تحویل

پیش‌نمایش مرحلهٔ ۷ متوقف و محیط موقت تازهٔ مرحلهٔ ۸ روی `http://127.0.0.1:8000/api/v1/docs` همراه Worker انقضای پنج‌ثانیه‌ای اجرا شد. readiness آماده، مستندات ۲۰۰، هشت مسیر متمایز appointments در OpenAPI و رد خواندن نوبت بدون نشست با ۴۰۱ بررسی شده‌اند. دیتابیس ماندگار و کانتینرهای پروژه‌های دیگر تغییر نکرده‌اند.

پرداخت واقعی یا Mock هنوز از API ساخته نمی‌شود؛ این موضوع مرحلهٔ ۹ است. شواهد مالی فقط در fixture آزمون ساخته شدند، درگاه و پرداخت ساختگی قابل درخواست از مرورگر نیستند. رخدادهای Outbox پایدارند، ولی مصرف اعلان و رسیدگی Refund به مراحل مربوط موکول است. محیط ماندگار باید Worker مستقل سالن را اجرا کند. ورود موبایلی بدون ایمیل حفظ شده و OTP هنوز به آینده موکول است.
