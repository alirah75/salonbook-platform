# گزارش بررسی مرحلهٔ ۲

تاریخ: ۲۰۲۶-۱۰-۰۱. محیط: Windows، Python 3.13.5 و PostgreSQL 18 در Container موقت با Image ثابت. این گزارش مربوط به Schema و قراردادهای تراکنشی لایهٔ داده است؛ آزمون API، احراز هویت عملیاتی یا درگاه واقعی محسوب نمی‌شود.

| بررسی | نتیجه |
|---|---|
| pytest، مجموعهٔ کامل | ۸۳ موفق، بدون شکست، Skip یا هشدار؛ ۱۴٫۹۴ ثانیه |
| Ruff | موفق |
| Ruff Format | ۴۲ فایل قالب‌بندی‌شده و سازگار |
| mypy با حالت strict | موفق؛ ۳۹ فایل بررسی شد |
| ارتقا → بازگشت به base → ارتقای مجدد | موفق روی دیتابیس خالی مستقل |
| Alembic check | بدون اختلاف بین مدل و Schema پس از هر ارتقا |
| کاتالوگ RLS و قیود PostgreSQL | ۴۳ جدول با ENABLE/FORCE RLS؛ همهٔ Constraintها validated |
| بازتولید ERD، فرهنگ داده و SQL | خروجی‌ها با مدل و migration یکسان |
| uv sync --frozen | پس از رفع مشکل نصب اولیه موفق |
| پاک‌سازی محیط آزمون | Containerهای مخصوص این آزمون در پایان متوقف شدند |

موارد مهمی که با داده و SQL واقعی بررسی شدند:

- خواندن و نوشتن بین سالن‌ها، FK بین‌سالنی و عدم باقی‌ماندن Tenant روی اتصال Pool پس از Commit و Rollback.
- اعمال FORCE RLS به مالک غیرSuperuser و منع دسترسی Runtime به هویت پلتفرم، registry اصلی دامنه و TRUNCATE.
- انتشار فقط hostname فعال و تأییدشده در View تشخیص سالن.
- رقابت ۵۰ درخواست با قفل‌های کنترل تقویم، مشتری و متخصص: **یک Commit موفق و ۴۹ خطای تداخل**.
- جلوگیری از تداخل متخصص بین دو لاین، احتساب Buffer، اجازهٔ بازه‌های مجاور و حفظ زمان قبلی در جابه‌جایی ناموفق.
- ادامهٔ اشغال Hold منقضی تا تغییر صریح وضعیت؛ جلوگیری از فرض اشتباه پاک‌شدن خودکار Index با عبور ساعت.
- الزام تطبیق مبلغ سفارش، جلوگیری از دو Attempt باز هم‌زمان، یکتایی مرجع دریافت و حداکثر یک Allocation.
- حفظ دریافت واقعی دوم یا مبلغ نامنطبق برای رسیدگی، همراه با منع تخصیص نامعتبر به سفارش.
- تغییرناپذیری Snapshot، Audit، دریافت‌ها، رسیدها، فاکتورها و دفتر گردش، حتی هنگام استفاده از اتصال دارای دسترسی مدیریتی عادی.
- جلوگیری از Refund منفرد بیش از مبلغ منبع، ساخت مبلغ دلخواه در دفتر گردش و ترکیب حساب واقعی با پرداخت آزمایشی.
- حفظ Snapshot تجاری هنگام تغییر متخصص تخصیص‌یافته، یکتایی RoleAssignment با Line تهی و اعتبار ساختار Calendar.

در بازآزمایی اولیه، رقابت بدون قفل هماهنگ به deadlock منجر شد؛ Double Booking رخ نداد. پروتکل قفل ثابتِ معماری در آزمون نهایی اعمال شد و نتیجهٔ فوق به دست آمد. پیاده‌سازی این پروتکل و retry محدود در Service مرحلهٔ ۸ همچنان لازم است.

قواعد تجمیعی مانند جمع چند Refund، جمع اقلام، ماشین انتقال وضعیت، تطبیق تقویم، Verify درگاه و مجوز لاین، در مراحل مربوط به Service و API آزمون خواهند شد. موفقیت این مرحله ادعای تکمیل کل محصول یا آمادگی انتشار Production نیست.
